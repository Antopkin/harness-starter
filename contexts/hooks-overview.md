# Hooks overview

Read this when you are editing `.claude/settings.json`, debugging a guard, or blocked by one. The guard scripts live in `hooks/` at the root of this starter, and the exact wiring lives in `.claude/settings.json`; this file says what each guard does, which tool runs it, and why.

The guards that match on patterns are speed bumps rather than walls: they stop an agent that runs a dangerous command by accident or on a literal instruction, not an agent determined to get around them. Leave the pattern sets as they are unless you mean to change the policy, and review the whole set when the model changes.

## Which tool runs which guard

| Guard | Event | Claude Code | OpenCode | Codex |
|---|---|---|---|---|
| `../hooks/bash-guard.sh` | before a shell command | yes | yes, through the bridge | no |
| `../hooks/skip-ci-guard.sh` | before a shell command | yes | yes, through the bridge | no |
| `../hooks/file-guard.sh` | before an Edit, a Write, a MultiEdit or a NotebookEdit | yes | yes, through the bridge (edit, write, multiedit, and patch and apply_patch with every path in the patch checked) | no |
| `../hooks/read-guard.sh` | before a Read or a Grep | yes | yes, through the bridge (read and grep) | no |
| `../hooks/pasted-key-guard.sh` | on prompt submit | yes | no | no |

Claude Code runs the guards natively: `.claude/settings.json` wires each one as `bash "$CLAUDE_PROJECT_DIR/hooks/<name>.sh"`. OpenCode reaches the same scripts through a plugin, described below. For Codex, this starter does not wire Codex hooks yet; the rules apply as AGENTS.md prose, backed only by Codex's own sandbox and approval settings.

## Before a Bash call

Two scripts run in order. `../hooks/bash-guard.sh` blocks the irreversible commands. A check over the whole command refuses `--no-verify` and `sudo` followed by a space wherever they appear. A per-word pass then cuts the command into segments at `;`, `&&`, `||`, `|`, `&`, parentheses, backticks and newlines (a backslash-newline continuation is joined, and both the raw and the joined text are scanned), strips quotes and backslashes, and analyses every word named `rm` or `git`, so environment prefixes, `bash -c '...'` and `xargs rm` are covered; git's global options such as `-C <dir>`, `-c <key=value>`, `--git-dir <dir>` and `--config-env <spec>` are skipped before the verb is read. Every later word of the segment counts wherever it stands, so moving a flag before or after the other arguments does not get the command through. The pass refuses:

- `rm` whose words ask for both recursion (`r` or `R` in a short option cluster, or `--recursive` or a prefix of it) and force (`f`, or `--force` or a prefix of it), together or apart, in any order;
- `git reset` with any word starting with `--h`, which catches `--hard` and every abbreviation of it; only `--help`, spelled out exactly, is let through, so `git reset --help` still opens the manual;
- `git push` with `f` in a short cluster (`-f`, `-uf`), `--force` or its prefixes down to `--fo`, or a refspec starting with `+`; `--force-with-lease` stays allowed;
- `git commit` with `n` in a short cluster (`-n`, `-an`) or any prefix of `--no-verify` from `--no-veri` on. A cluster stops at an option that takes a value (`m`, `F`, `C`, `c`, `t`), and that value, attached or in the next word, is skipped as one shell word, quotes included; `u` and `S` end a cluster with their value attached, so `-u -n` and `-S -n` are refused. So `git commit -m "fix -n handling"`, `-m -n`, `-F -`, `-uno` and `--no-verbose` stay allowed;
- `git commit` and `git push` when a global `-c` or `--config-env` sets `core.hooksPath`, in any letter case, since that switches the hooks off as surely as `--no-verify`;
- `git checkout` and `git switch` with `f` in a short cluster (the cluster stops at `b`, `B`, `c` or `C`, whose value is a branch), `--force` or its prefixes down to `--f`, or `--discard-changes` or its prefixes down to `--di`;
- `git clean` unless it carries `-n` (alone or in a short cluster such as `-nd`) or `--dry-run` before any `--`. A later `--no-dry-run` (or a prefix of it from `--no-d` on) cancels the dry run, and in a cluster ending in `e` (`-fe`) the next word is the exclude pattern, so an `n` there is not read. Every force spelling and a `-c clean.requireForce=false` override are refused alike;
- a whole-tree `git checkout` or `git restore`: a pathspec of `.`, `./` or `:/`, a pattern made only of `*`, `?`, `[` and `]` (`*`, `**`, `?*`), one that normalises to the root (`./.`, `.//`, `src/..`), a bare `:(top)` or `:/`, an exclude-only pathspec (`:!x`, `:^x`, `:/!x`, `:(exclude)x`), which means the whole tree except `x`, a `:(magic)` without `top` read like the pathspec after it (so `:(icase).` counts as `.`), or `--pathspec-from-file`, whose list the guard cannot see. `git restore --staged` (or `-S`) alone touches only the index and stays allowed; with a worktree mode (the default, `--worktree` or an abbreviation of it, `-W`) or `--no-staged` it is refused.

Before the per-word pass runs, the guard takes out the parts of a command that are data rather than code. A heredoc body counts as data when its delimiter is quoted (`<<'X'`, `<<"X"`, `<<-'X'`) and no word of the marker line names a shell or an interpreter: `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `ssh`, `eval`, `source`, `.`, `xargs`, `env`, `sudo`, `python*`, `node`, `deno`, `bun`, `perl`, `ruby`, `php`, `osascript`, `awk` or `sed`. The whole marker line is checked, not only the word before `<<`, so `cat <<'X' | bash` counts as an interpreter too. That is what lets `git commit -F - <<'MSG'` carry a message that names the very commands it explains. The marker line itself is scanned in full, text after the marker included (`cat <<'X' && ...` is still read), and so is everything after the terminator line. The body of an unquoted delimiter is scanned, because the shell expands `$(...)` in it, and the body an interpreter reads is scanned with its quotes, commas and brackets turned into spaces, so a dangerous command inside `os.system('...')` in a `python3 - <<'X'` body is caught. In the same way, the value of `git commit -m`, `-F`, `--message` or `--file` is data up to its own end, its closing quote or the end of an unquoted word: text after it on the same line is scanned as usual, and whatever follows a `$(` or a backtick inside the value is read as a command. So `git commit -m "document the -n flag of grep"` is allowed, while `git commit -m "$(...)"` with a dangerous command inside is refused.

The guard also refuses any command that names the Claude Code credential store, `.claude.json` in any letter case (the file lives in your home directory): that is the shell half of the read guard below. That check and the one for `--no-verify` and `sudo` read the whole command, heredoc bodies included. The price of reading every word is that an `echo`, or a commit message passed in any other way, that spells one of these commands out is refused too. The guard reads words as written and expands nothing: a git alias defined with `-c alias.x=...`, a shell alias and command substitution such as `$(which rm)` all go past it. If the per-word pass itself fails to run, the command is refused.

`../hooks/skip-ci-guard.sh` blocks a `git commit` that asks to skip CI unless every file it would commit is documentation: a `.md` or `.txt` file, anything under `docs/`, or a `LICENSE` file. The markers it knows, in any letter case, are `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` and `[actions skip]` (with a space, `-`, `_` or nothing between the words), `***NO_CI***` and a `skip-checks: true` trailer. It checks the staged files; when the same command stages files itself (`git add`, or `git commit` with `-a` or `--all`), every change against `HEAD` as well; and with `--amend`, the files `HEAD` already touches. A push with the `ci.skip` push option (`git push -o ci.skip`, `--push-option=ci.skip`) is refused whatever the files, because it skips CI for every pushed commit and the guard cannot see which files those touch; other push options pass. It finds the repository from `git -C <dir>`, else from a `cd <dir>` in the command, else the current directory. Past its `jq` check it is a tripwire only: when git cannot list the files, it warns and lets the commit through.

## Before an Edit or a Write

`../hooks/file-guard.sh` runs for Edit, Write, MultiEdit and NotebookEdit. It takes the target from `file_path`, falling back to `notebook_path`, and blocks writes to protected and secret paths, matching case-insensitively because a case-insensitive file system opens `.ENV` as the same file as `.env`: environment files (`.env*`, with `.env.example` and `.env.sample` left writable), anything under `.git/`, a worktree's `.git` file itself, anything under a `secrets/` directory, and narrow credential files, whose name ends in `.txt`, `.json`, `.env`, `.pem` or `.key` and either contains credential or secret or carries token as a word of its own (`token.json`, `api_token.json`, `gh-tokens.json`). So `tokenizer.json`, a design-token `tokens.json` and ordinary source files stay editable. The permission rules in `.claude/settings.json` add two deny rules on top, for `Edit(**/.env*)` and `Edit(**/.ssh/**)`.

The two kinds of guard look in different places, and that difference decides how an instruction file gets written. The Bash guard matches its patterns against the **whole command string**, only a quoted heredoc that no interpreter reads and the value of a commit message set aside, so an unquoted heredoc or an `echo` that merely *documents* a dangerous literal is refused on the strength of the text it carries rather than on what it would do — writing down what a recursive force delete, a hard reset or `--no-verify` looks like is enough. The file guard never sees that text at all: Write and Edit carry their payload in `tool_input.content`, which the file guard does not inspect, because it decides from the target path alone. So instruction files (skills, agents, contexts, `AGENTS.md`) are written with Write and Edit, never through a shell heredoc, an `echo` or a redirect. That is a fact about where each guard looks, not a style preference, and it holds over any session guidance that prefers Bash for edits. A wave prompt therefore states the rule in as many words instead of leaving each agent to work it out. Left unstated, it collides with that guidance, and every agent in the wave settles the collision on its own, independently and silently — which is not a thing anyone reading the transcripts afterwards can see going wrong.

## Before a Read or a Grep

`../hooks/read-guard.sh` stops the Read and the Grep tool from opening the Claude Code credential store (a file named `.claude.json`, which lives in your home directory) and its backups (`.claude.json.backup` and the like), and environment files (`.env*`), with `.env.example` and `.env.sample` left readable. It checks the Read tool's file path and Grep's path and glob, each on its own, so a Grep over a directory with a glob naming the file is caught too, and it matches case-insensitively because a case-insensitive file system opens the same file under any spelling. A Grep glob is also read the way the glob engine reads it: its braces are expanded, and the last segment of each expansion is tried as a shell pattern against `.env`, `.env.local`, `.claude.json` and `.claude.json.backup`, so `{.env,x}`, `[.]env` and `*.local` are refused. The price is that a glob of `*` or `**` alone is refused too: Claude Code's Grep searches hidden files, so such a glob would reach `.env` and the credential store. Name the files you want (`*.md`, `src/**/*.py`) instead. A glob with more than 512 brace expansions is refused as too complex to check. It runs in Claude Code and, through the bridge, in OpenCode. Reads through the shell are only partly covered: the Bash guard refuses any command that names the credential store, but a `cat` of an `.env` file goes past both guards, so the rule against reading secrets still has to be kept by hand there. It guards against an agent reading a file by accident or on a literal instruction; it is not proof against a caller that already runs arbitrary code.

## On prompt submit

`../hooks/pasted-key-guard.sh` refuses a prompt with an API key or a private key pasted in plain text, so the value never lands in the transcript. It recognizes a small set of high-signal shapes: Anthropic keys, OpenAI project, service-account and admin keys (`sk-proj-`, `sk-svcacct-`, `sk-admin-`) and legacy user keys (the `T3BlbkFJ` marker), Stripe live secret and restricted keys (`sk_live_`, `rk_live_`), GitHub classic and fine-grained tokens, GitLab personal access tokens (`glpat-`), Google API keys (`AIza`), AWS access key IDs (`AKIA` and `ASIA`), Hugging Face tokens (`hf_`), Slack tokens, and PEM and PGP private-key blocks. A masked example whose body is only a run of X is let through, so the format can still be discussed, and so is an AWS key whose body ends in `EXAMPLE` (AWS's own documentation key). Every match in the prompt is checked, so a masked example cannot shield a real key after it. It lets an empty prompt through. It uses only bash's builtin pattern matching, so it needs neither `jq` nor `grep`: a missing tool never blocks your prompts and never lets a key through. This guard exists only in Claude Code. OpenCode has no prompt guard, so there the rule is simply not to paste keys into the chat.

## The same guards in OpenCode

OpenCode reads `AGENTS.md` natively and reuses the skills from `.claude/skills/` or `.agents/skills/`, so adding a skill needs nothing extra. Two surfaces need attention.

**The guards** reach OpenCode through `../hooks/opencode-guard-bridge.js`, installed as an OpenCode plugin; `INSTALL.md` at the repository root has the exact commands. The plugin module exports one thing, `ClaudeGuardBridge`, because OpenCode's loader refuses a plugin with any export that is not a function; the test reaches the check through `ClaudeGuardBridge.testing`. The bridge reads the `PreToolUse` hooks out of the project's `.claude/settings.json`, merged with those of `.claude/settings.local.json` when that file exists, and never reads settings in your home directory. It translates OpenCode's tool names and camelCase arguments into the JSON the guard scripts already parse (grep's `include` becomes the `glob` the read guard checks), and refuses the call when a script exits 2. The project root is OpenCode's worktree, or its directory when the worktree is `/`, as it is for a project outside git. So a new guard is still one edit to `.claude/settings.json`, and the bridge needs no attention.

`multiedit`, `patch` and `apply_patch` count as Edit, so they go through the file guard too: `multiedit` is checked by its file path, and for `patch` and `apply_patch` the bridge reads every path the patch text names (added, updated, deleted or moved to) and refuses the whole call if any one of them is protected. For the tools that can change something (bash, edit, write and those three) the bridge fails closed: a patch that is missing, unparseable or names no file, a settings file that cannot be read, settings that wire no guard for the tool (`no guard wired for <Tool>`), a guard script that cannot be started (exit 126 or 127, or a spawn error), and a guard that does not finish (`guard did not finish`: killed by a signal, an exit status of 128 or more, which is how a shell reports a child killed by a signal, or still running after its 60-second timeout) all end in a refused call rather than one let through unchecked. For read and grep the same problems are logged and the call proceeds. Only exit 2 is a verdict: any other non-zero exit is logged and does not block. Its own test is `../hooks/opencode-guard-bridge.test.mjs`, which exercises the real scripts; run it after changing a guard's matcher, because a matcher that stops matching fails silently.

Two gaps remain in OpenCode. There is no pasted-key guard, so do not paste keys into the chat. And the `permissions.deny` rules of `.claude/settings.json` are not applied, because the bridge carries over the hooks only; if you want the same deny rules there, repeat them in OpenCode's own permission settings.

**The agents** must be regenerated, because the two tools disagree about frontmatter: Claude Code reads `tools:` and `model:`, OpenCode reads `mode:` and a `permission:` object. After editing anything in `agents/`, run `python3 hooks/opencode-agents-sync.py` from the repository root to see what would change, and add `--apply` to write it. The script writes only to `.opencode/agent/` and `.opencode/agent-retired/` in the current directory and never touches your home directory; `.opencode/agent/` is derived and is never edited by hand. A role whose `tools:` list omits Write, Edit or Bash, or whose `disallowedTools:` names one, gets the matching OpenCode permission (write, edit or bash) denied; a role granted Edit keeps edit allowed. A role whose tool restriction the script cannot translate faithfully (an empty `tools:`, or a `disallowedTools:` entry with no OpenCode mapping) is never generated as an unrestricted agent: the script reports it, retires any earlier copy to `.opencode/agent-retired/`, and exits 1.

OpenCode loads its configuration once at startup and does not reload it, so any change here takes effect on the next run, not the next prompt.

## Known limits

- Claude Code blocks a call only when a guard exits with code 2. A guard that times out, is killed or exits with any other code is treated as non-blocking, so a hung guard fails open there; only the OpenCode bridge fails closed.
- A shell read of an environment file (`cat .env`) is not guarded: the read guard covers only the Read and Grep tools, and the Bash guard covers only the credential store.
- The Bash guard does not expand command substitution or aliases, so `$(which rm)` or a shell alias for `rm` goes past it.
- OpenCode has no pasted-key guard and does not apply the `permissions.deny` rules of `.claude/settings.json`.
- This starter does not wire Codex hooks yet; there the rules apply as AGENTS.md prose only.

## User-invoked skills

A skill whose frontmatter says `disable-model-invocation: true` is meant to run only when you type its name. That flag holds only in Claude Code. OpenCode and Codex ignore it and may still invoke such a skill on their own when a request matches its description, so in those tools treat "user-invoked" as a convention, not a guarantee.

## Verifying a change

After editing the guard scripts or the hooks block in `.claude/settings.json`, run `bash hooks/hooks-selftest.sh` from the repository root and expect exit code zero. It feeds simulated hook input through the real command strings from the settings file, which catches quoting and path bugs that a check of the patterns alone would miss.

## What the hooks need installed

Install `jq` first (`brew install jq` or `apt install jq`). Every guard that parses the JSON hook input with `jq` fails closed when `jq` is missing or when it fails: the guard exits 2 (without `jq` with "guard inactive: install jq"), so the tool call is refused rather than let through unchecked. The pasted-key guard is the exception and needs neither `jq` nor `grep`. Node or bun runs the OpenCode bridge and its test, and `python3` runs the agents sync.

## Options you may add

The starter does not ship network deny rules, but you can add them. Permission deny rules for `curl`, `wget` and `nc` in `.claude/settings.json` (for example `Bash(curl:*)`) stop an agent from sending data out through the shell; the cost is that every legitimate download then needs your approval. Likewise, a Python formatter after edits, desktop notifications and a memory snapshot before compaction are easy to add as hooks of your own, and none of them is part of this starter.
